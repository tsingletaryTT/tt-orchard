Part of #731.

## What

The stage 2 check's fidelity score needs about 4,000 scored tokens to tell bfp8 from bfp4 (issue 731: 9.991 against 9.821 on the Olmo-Hybrid-7B port), and the check stopped at a fixed `MAX_POSITIONS = 64`. The calibration runs used a raised copy of the template. The cap is now a recorded, validated setting.

- `--port-check-positions N` on the supervisor and on `tt-orchard bringup`: a whole number from 16 to 8192, default 64. The supervisor writes it into `port_check_config.json` as `max_positions` and into `run_start` as `port_check_positions`, both only when it is not the default. A run that does not name the option has the files it had before. A resume keeps the recorded value and refuses another one.
- The template reads `max_positions` (a value outside the range stops the run before the port loads, with kind `setup`) and scores the smaller of the cap and the stage 1 reference's length. Its record has `positions` = `{cap, scored, reference_length}`. The fidelity note says which of the two limited the count.
- The gate recomputes the block. The cap is in range and equals the config's `max_positions`. The positions scored equal the number the record compares and the smaller of the cap and the reference length. The reference length equals the stage 1 file's. A record with no block ran with the default cap, so it may not compare more than 64 positions and its config may not set another cap.
- The fidelity value stays report-only. Nothing here gates on it.

Finding: stage 1's reference decodes 32 tokens (`N_NEW` in the reference gate). A cap above 32 therefore changes nothing today, and the 64 was never the binding limit of a real run. The record now shows this (`reference_length` next to `cap`). Scoring 4,000 tokens also needs a stage 1 reference of that length, sampled at temperature 1 as the calibration did. That is not part of this change.

## Hardening checklist

1. Wrong type or shape in input: yes. `check_positions` and `positions_cap` take only a whole number in range (booleans, floats, strings, `None` and `10**400` refused, `test_check_positions_refuses_everything_else...`, `test_a_key_out_of_range_or_of_the_wrong_type...`); the gate refuses a block that is not an object, has other keys or holds a non-integer (`test_the_gate_refuses_a_block_...`, `test_the_gate_refuses_a_cap_outside_the_range_or_not_a_whole_number`).
2. Files something else controls: yes. The gate's read of `port_check_config.json` goes through `safeio.read_json` with a size bound; the reader is in `tests/hostile_inputs.py` `READERS` (42 cases pass). It does not open a path or walk a tree, so no `hostile_fs.py` entry.
3. Check, then use: yes. The cap the gate compares with is the config the record hashed (the existing config hash check), and the supervisor puts the config back before the test (`test_a_coder_that_edits_the_config_during_prepare_gets_the_supervisors_cap_back`).
4. Evidence an agent can write: yes. The coder cannot change the cap: the supervisor rewrites the config, the record's `config.sha256` must match it, and the gate refuses a record whose cap differs from the config's (`test_the_gate_refuses_a_cap_that_is_not_the_one_the_config_sets`) or whose block was removed while the config sets a cap (`test_the_gate_refuses_a_record_whose_block_was_removed...`).
5. Verdicts and labels: yes. The block names its basis: the reference length is checked against the stage 1 file, and the note says which limit applied. The fidelity value is still labelled "reported, not gated".
6. The check inspects the same object the action uses: yes. The gate reads the config of the same stage directory the template ran in, and the reference length from the same stage 1 file the template read (`test_the_gate_refuses_a_reference_length_that_is_not_the_stage_1_reference`). Stage 4 entries pin the same config through the same function.
7. Parsers and matchers: yes. The positive and negative cases are the parametrized lists in the range tests (15, 16, 8192, 8193, `True`, `64.0`, `"64"`, a string of 400 digits).
8. Failure paths: n/a. The change adds no acquire; a bad cap stops the template before the port loads and before any chip is opened (`test_the_template_run_refuses_a_cap_below_the_range_before_it_loads_the_port`).
9. Numbers and sizes: yes. 0, -1, 15, 16, 4000, 8192, 8193, `10**20` and `10**400` are tested at the option, the template and the gate (a `10**400` in a record is refused with the whole record by the JSON reader, `test_a_cap_too_large_to_read_as_an_integer_is_refused_with_the_whole_record`). The upper limit's stated size is checked by `test_a_record_at_the_highest_cap_stays_far_below_the_gates_json_limit`. No new `float()` or `math.isfinite` call.
10. Secrets, paths and host names: n/a. No new output carries a path or a token. Reasons name the config file by its fixed name and bound the value they show.
11. Tests: yes. No skips. Each guard has a mutation that turns a test red (28 mutations, all red).
12. Housekeeping: yes. `changes/fidelity-position-cap.toml` (0.9.188; the other open PRs also claim 0.9.188, so one of them needs a new target at merge), a dated entry at the end of `docs/project-log.md`, the README flag row (`tests/test_readme.py` passes), `python3 scripts/version.py check` ok.
