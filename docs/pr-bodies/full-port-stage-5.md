# Full port stage 5: the port behind a chat server, with an acceptance corpus replayed at boot (issue 329, stage 5 half)

Branch `full-port-stage-5`, off the local `integration` branch. Not a pull request yet. No publish, no push to Hugging Face, no hardware, no real telegraph call.

## What it does

After stage 4, a full-port run (`--full-port`, class `full-port`) reaches stage 5. No agent works in it.

1. The supervisor takes the port that passed stage 3 (or stage 2 when stage 3 was skipped), copies its files to `stages/5/port/` and records the sha256 of each in the ledger.
2. It records an acceptance corpus (`orchard/full_port_serve.py`, `build_corpus`) from the stage 1 reference files and the accepted port-check record. The record's sha256 must be the one the ledger holds for the file that stage's gate accepted.
3. One command runs under a lease of the chips the accepted stage used: `python3 -P -s stages/5/port_serve.py`. The template runs the port in stage 2's worker, puts a loopback chat server in front of it (the pattern of `scripts/minicpm3/serve.py`), replays the corpus through `/v1/completions`, and refuses the server when any position differs. It then prints a `READY` line, asks a passkey question at two or more lengths through `/v1/chat/completions` (each twice), and asks a canary (a prompt, a different prompt, the first prompt again).
4. The supervisor writes `result.json` from the record. The gate recomputes every figure in it.

`--full-port-rehearsal` waives the field `coherent` (the passkey was answered at every length) and nothing else.

## The twelve checklist answers (docs/pr-hardening-checklist.md)

1. **Wrong type or shape in input.** Every field the gate takes from the record, the result, the corpus and the config is type-checked before use (`full_port._ids`, `_num`, `_int`). Tests parametrize 7 sections of the record with `None`, a list, a string, a number and `{}`, and 8 result fields with `None`, `[]`, a string, `{}` and `-1`; each gives a reason and no exception. The server rejects a bad `prompt`, `max_tokens`, `forced_tokens` and `messages` with a 400 (tests in `test_full_port_serve.py`). A NUL in a path is handled by `full_port._inside`, which the gate reuses.
2. **Files that something else controls.** The gate reads the record, result, marker, corpus and config through `safeio` (`full_port._json`, `_sha`). The port copy refuses links, devices and FIFOs, caps files, entries, depth and size, and writes with `safeio.atomic_write`. No new reader was added to `tests/hostile_inputs.py` (see item 11). The template's own file accesses carry `# hardening: ok` with the reason: the supervisor wrote those files before the test and the gate compares their hashes.
3. **Check, then use.** The corpus hash is taken from the bytes written and goes into the ledger before the test; the gate compares the file on disk with the ledger's value and with a corpus rebuilt from the stage 1 files. The template runs the worker from the bytes whose sha256 it compared. The accepted record's hash is compared with the ledger's before the corpus is built.
4. **Evidence an agent can write.** No agent works in stage 5. The test marker must be the file the supervisor recorded in the ledger (the same check as stages 2 and 3, applied through the stage's skill name). The chip count, the source stage, the corpus hash and the rehearsal flag come from the supervisor and the ledger, never from a file in the stage directory. A test shows a `rehearsal: true` field in `result.json` waives nothing. Not covered by a supervisor-level test: a marker rewritten between the test and the gate (nothing writes there in this stage); the shared check is tested in the stage 2 and 3 suites.
5. **A verdict stronger than its evidence.** `result.json` carries `limits` and `labels`. `corpus_matched`, `corpus_positions`, the reference agreement, the passkey answers, the ready line and the cache flag are each recomputed from the record. `checks.passkey.pass` is true under the rehearsal option only because the option was given, and the result keeps `coherent: false` next to it.
6. **The check looks at a different object than the action uses.** The served port files are compared by name and sha256 with the `port_sources` of the stage 2 or 3 record that built the corpus. A test edits a served file and its record together and the gate refuses it. The chip count of the test is compared with the chips of the stage the port came from (2 for stage 2, 4 for a stage 3 run on four chips, tested in two setups).
7. **A parser or matcher that is too broad or too narrow.** The `READY` line must match one pattern in full (`READY <model> on 127.0.0.1:<port> pid <pid> corpus N/N positions`) and appear once in the output. The mark line is matched at line start, and a second one is refused. A test supplies a line that admits a partial replay (79 of 80).
8. **Failure paths that leave state behind.** The template stops the server and the worker in a `finally` (the worker also kills the port's child processes, as in stage 2). A failed replay leaves no record file. The port copy removes the old `stages/5/port/` before copying. The hardware lease path is the existing one (`_hardware_phase`, widened to the source stage's chips).
9. **Numbers and sizes.** The port copy has caps (200 files, 2 MiB each, 1000 entries, depth 8). The passkey lengths are bounded (at most 8192 tokens, never above the context minus 64) and a context too small for two lengths is refused at prepare. `max_tokens` is 1 to 4096 and the request body at most 8 MiB. Tests use 0, -1, too large and a prompt longer than the context.
10. **Secrets, paths and host names.** The record holds the cache directory with `$HOME` shortened to `~`. The ledger entries hold hashes, counts and port file names only. The skill and README name no machine path. The repo test for `/home/` and `/mnt/` in `orchard/skills` passes.
11. **Tests that do not test the claim.** 39 mutations, each removing one guard, each turned a test red (list in the project log). One mutation (teacher forcing dropped) was first green because the fake port's own greedy run equalled the reference; a test with a port that is wrong at one position was added and turned it red. The template runs as a real subprocess against a fake `ttnn`. Hostile-input registry entries for the new gate were not added: it reuses `full_port._json`, which stage 2 covers.
12. **Housekeeping.** `changes/full-port-stage-5.toml` (target 0.9.117, chosen to avoid the default 0.9.115 that two parallel forks will also take), a dated project-log entry, a README note (no new flag), `python3 scripts/version.py check` passes.

## What a pass shows, and what it does not

It shows that the port, running behind the server, answers the recorded positions with the ids it gave in stage 2 or 3, that those ids agree with the CPU reference at the stage 2 bar, that a request in between does not disturb the canary, and that the passkey prompts are accepted and answered the same way twice. For the tiny random-weight model the corpus is token-level agreement of the port with itself and with the CPU reference. It does not show correctness at positions or lengths that stage 1 did not record (the passkey prompts have no CPU reference), speed, or concurrent requests. The kernel-cache figure counts files before the boot. It is not the runtime's hit counter.

## Not tested without hardware

A real `ttnn` device open on 1, 2 or 4 chips; the real model's passkey answer; the boot time and the kernel cache on a real box; a port that prefills one token per step at the 8192-token passkey length (the 3600 s deadline may be short); the real chat template of a real tokenizer (the fake snapshot has none, so the `plain` form ran); the lab path (`_lab_hardware_phase`) with stage 5.
