# Stable Audio 3 small music as a v6 thin bundle: a can for an audio model (2026-10-30)

Goal (operator): "v6 thin bundles for all these ... this is like the canning step", and for every can's card: "note things on the cards. benchmarks. use the tt-model-manager vernacular for model cards. tt-model-ranker helps us understand what good is." Model: `stabilityai/stable-audio-3-small-music` (revision `8bdfb53c6b0fbc62113cd571fd37373efe15fa14`, license `other`) on one Blackhole chip. Pattern: `docs/canning.md`; card conventions: `docs/can-cards.md`. Nothing was uploaded, published or merged. The private repository `episod/stable-audio-3-small-music-blackhole` was not touched, and its visibility is unchanged (the operator has not given the legal sign-off).

## What was built

- `pkgsrc/server/stable_audio_asgi.py`: the ASGI front end. It imports the job server (`pkgsrc/server/stable_audio_jobs.py`, an unchanged copy of `serve/serve_audio.py` of the tt-stable-audio-3-small-music repository, sha256 `9cf9bd06...`, the same bytes as the recipe package's `demo/serve_audio.py`) and serves its routes under uvicorn. It keeps one resident chip runtime loaded; the device opens in the lifespan startup and `/health` answers 200 only after the weights are on the chip.
- `orchard/can.py` (general changes, about 90 added lines): `[[extra_tree]]` copies a directory into `extra_code/`; `[check] mode = "audio-job"` selects the new boot check in `orchard/can_audio.py`; `boot_check` takes `job_timeout`.
- `orchard/can_audio.py`: two jobs with the same settings, each clip downloaded and its length read from its own header, both times recorded (the first runs against a kernel cache the copy has never filled).
- `scripts/can_stable_audio_base.py`: builds the base directory the spec is staged from. The model library (`stable_audio_3`, MIT, not on PyPI), the license files and the weights pointer are not in this repository, so the script copies them after checking the library checkout's commit (`77e0398c...`) and that it is clean, and that the snapshot directory is named for the pinned revision. It renders the card with the license paragraphs cut word for word from the license copy.
- `scripts/can_stable_audio_numbers.py`: merges the raw session files into the evidence files and computes the card's numbers from them.
- `pkgsrc/tools/audio_client.py` (a stdlib client shipped in the bundle) and `pkgsrc/tools/cpu_floor.py` (CPU timing with the same code and weights).
- `config/can.stable-audio-3.toml`, the card template `pkgsrc/can/stable-audio-3-README.md`, `docs/can-cards.md`.

The staged bundle has 69 files and 1 MB (no weights, venv or cache). It passes the gate.

## Hardware (board 1, chips 2 and 3, `gozer acquire --chips 1`, then `gozer run`; each lease released and reset cleanly; no chip wedged)

Host: 16 cores shared with the other cans' agents; one-minute load average 16 to 44 during these runs. Every time below depends on that load.

1. First install: `uv` refused `tqdm==4.70.1`. `install.sh` adds the PyTorch CPU index as an extra index and uv takes a package from the first index that has it; that index has tqdm only up to 4.66.5 and packaging only up to 24.1. Both pins were lowered (the library's metadata asks for newer ones; its code is copied, not installed, and uses neither in a new way). After that the install took 29 to 45 s and the verify statements passed (`import stable_audio_3.model_configs` works with numpy 1.26.4 and torch 2.7.1).
2. `tt-orchard can boot` on a copy of the first staged bundle: ready in 21 s, first 10 s clip 41.7 s (empty kernel cache), second 1.2 s, rtf 0.123; all checks passed. On the final bundle (README and evidence differ from the first one; the code is identical), with the host at load 44: ready 33 s, first clip 116.2 s, second clip 7.8 s (rtf 0.781); all checks passed, `booted: true` in the ledger entry of the scratch run. The boot check's `max_rtf = 1.0` leaves little margin on a host this loaded; as with Granite, a boot check on a loaded host can fail on the rate alone.
3. Bench sessions (`evidence/session-*.json`; numbers on the card): the first 10 s clip after a start with an empty kernel cache took 38 to 92 s (median 49 s over 4 processes); with the kernel cache on disk it took 2.65 s. Later clips: 10 s in 1.1 to 17 s depending on the session's host load, 120 s in 6.4 to 20 s.
4. tt-model's own installer (`tt_kernel.cli._install_self_contained` into a scratch directory, scratch index, `HF_HOME` pointing at the existing cache) took 29.4 s, and `tt-model serve local/stable-audio-3-small-music-blackhole --local-only --port 20174` was healthy after 17 s and served 10 s and 120 s clips.
5. One start failed once with `UMD: Sysmem mapped at unexpected NOC address` while another agent's process was starting on the other board. The same command succeeded a minute later. Not investigated further.

## Against the recipe package

Same: routes, request checks, queue, limits, `/health` behaviour, the decoder on the chip, the clips. The clip samples of the bundle are bit-identical to the recipe package's for the 10 s and the 120 s clip (seed 42, same settings; FLAC samples compared; `evidence/clip-comparison.json`), through `can boot`'s copy and through tt-model's installer. The recipe package ran in the source environment (numpy 2.5.3, torch 2.7.0); the bundle runs numpy 1.26.4 and torch 2.7.1. The open question of Granite's log (agreement under the numpy 1.26.4 pin) is answered for this model by identity with the recipe's clips.
Different: (a) the model stays loaded, so a warm 10 s clip takes about 1 to 3 s where the recipe package takes 21 to 23 s (a new process for each clip, 7 to 9 s of it model load); (b) settings are environment variables; (c) the first request after a start compiles kernels in the bundle's own cache (38 to 92 s for a 10 s clip), which the recipe package also does on an empty cache; (d) the server accepts connections only after the model is loaded (uvicorn waits for the lifespan startup), where the recipe server answers `/v1/health` at once with `loading`; (e) the Gradio page of the recipe package is not in the bundle; (f) `run.sh` uses an HF cache inside the bundle directory unless `HF_HOME` is set, so a user without it downloads 3.4 GB; the card says so; (g) the job server copy lives in this repository (`pkgsrc/server/stable_audio_jobs.py`), and a change to the source repository needs a new copy.

## Accuracy

The chip clip against the CPU float32 clip of the same environment (10 s, seed 42; waveforms of the FLAC files): Pearson correlation 0.9676, relative L2 error 0.2526. The recipe package's own result file (2026-10-29, arrays before FLAC, a different CPU reference) had waveform correlation 0.9758 and relative L2 0.2190 and final-latent correlation 0.9905; the two measurements differ in what they compare and are not combined. Per-step bars (`orchard/step_bars.py`) were not run: they need a teacher-forced bfloat16 CPU run and a per-step chip check, and only the ACE-Step runner (`scripts/acestep/acestep_run.py`) writes those files. A runner for this model is not written.

## The card (tt-model vernacular) and the viewer

Conventions found and applied are in `docs/can-cards.md` (front matter and tags, section order and names, required sections, the performance table layouts, what never goes on a card). The card has no listening note: tt-model's guidance keeps opinions on the result off the card, and the measurements do not cover quality.

tt-model-ranker (`python -m card_viewer CARD --no-infer`, local file only), on the staged card: modality `audio` (from `pipeline_tag: text-to-audio`); window grade none, because the viewer has no audio grader ("Audio jobs are not graded yet") and the card has no speed table it can read as a text-model table; 29 measured rows read under "Expected performance" (it reads at most 30 rows per section, which set the number of rows in the table); family key `base:stabilityai/stable-audio-3-small-music`. Three findings changed the card: (1) the first draft put 37 rows in one table and the viewer dropped the last 7, which held the agreement numbers, so the table was cut to 27 rows and the agreement rows moved to an `eval | this package | reference | prompts` table in the layout the tt-model template asks for; (2) a word in the out-of-scope sentence made the viewer set the card's focus to speech, so the sentence was reworded; (3) `card_publish_gaps` (tt-model's own check) reports no missing required section. What the viewer still reports and the card cannot change: "The card names p150, p300c and quietbox, but the viewer found no numbers for it" (the table has no hardware column; the board is in the conditions paragraph).
