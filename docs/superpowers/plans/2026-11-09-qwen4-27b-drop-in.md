# Qwen4-27B (dense) as a drop-in on the QuietBox 2: full plan

Status (2026-11-09): approved by the operator. Milestone M0 (fallback ready, watcher armed) is in progress on branch `qwen4-drop-m0`. Tracks A and C are proposed as separate sessions.

## Context

Qwen4-27B (dense) is expected soon; no weights, config or chat template are public yet (checked 2026-11-09). The goal is
that on release day the only change is the weights pointer: the operator runs one check and one `tt-orchard bringup`
command, and orchard brings the model up through gozer on the existing **weights-only route** and ends with a tt-model v6
thin package, private on Hugging Face until the operator publishes.

Today that is not possible:
- The TT model code (cp8.1, the Qwen3.8-27B build that served on ports 20000/20001) only knows Qwen3.8's architecture.
  The reported Qwen4 adds hyper-connections (4 residual streams), a QSA sparse indexer on attention layers, and drops the
  layer norms; it may change the feed-forward width, the KV-head count and the delta-net gate.
- orchard would class Qwen4 as `full-port` (new tensors, missing norms). That route has only passed with an outside
  helper writing the port, and stage 7 does not package a full port.

What exists already:
- **Package and kit (built today):** private `mando2222/qwen4-27b-dense-v6-thin` iteration 0 = cp8.1 under the Qwen4
  name, proven on chips; build kit `~/qb2-unified-work/qwen4/` (`package.sh ITER [REPO]` with checked provenance,
  `api_check.sh`, `import_smoke.sh`, cards); model branch `qwen4` in `~/qb2-unified-work/thin/src` (worktree
  `thin/src-qwen4`) at cp8.1 `e3ab645`.
- **Team Qwen4 work in tt-orchard (tsingletaryTT):** `scripts/tiny_qwen4/make_franken.py` (Qwen3.8-27B weights in the
  dense `qwen4_exp` layout, identity hyper-connections that reproduce Qwen3.8 exactly in fp32, optional real QSA
  indexers from the higa2515 release, `--hc-sigma` perturbation, CPU proofs, teacher-forced reference);
  `scripts/tiny_qwen4/make_checkpoint.py` (random 4-layer checkpoints, `--width 27b`, `--set` overrides);
  `scripts/qwen4_ops_probe/` (on-chip probes: `p4_gated_residual.py` composes the hyper-connection math from ttnn ops and
  matched at PCC 0.99996; `p2`/`p3` validate ttnn's delta-net kernels; `p1` shows dilated depthwise `ttnn.conv1d` is
  wrong and gives a working shifted form; `common.py` holds ttnn-free torch references); the dense shim
  `orchard/skills/reference-gate-templates/qwen4_dense.py`; Qwen4 hazards in `orchard/hazards.py`; the pending
  frankenmodel chip run (spec `docs/superpowers/specs/2026-11-08-qwen4-franken-design.md` §6, issues #646, #579).
- **Reference math:** transformers 5.19.0 `qwen4_exp` (in the reference venv) defines every Qwen4 piece exactly
  (summary in Appendix A).

Release-day target: **nobody has to start anything.** A scheduled watcher (D3) sees the release appear on the Hub,
checks it, notifies the operator, starts the orchard run as soon as the chips are free, and reports when the run ends.
What the watcher runs, in full:
```
tt-orchard drop-check Qwen/Qwen4-27B --bundle mando2222/qwen4-27b-dense-v6-thin   # config + tokenizer only
tt-orchard bringup Qwen/Qwen4-27B --base mando2222/qwen4-27b-dense-v6-thin        # covered: weights-only route
tt-orchard bringup Qwen/Qwen4-27B --base mando2222/qwen3.8-27b-dflash2-vision-p300x2-q4kv-v6-thin --full-port   # not covered
```
The operator then reviews `stages/8/bundle` and says yes before stage 7's package is pushed or published.

## Approach

Move the port before the release, and make the release look like a weights swap:
1. **Track A, model code:** teach the cp8.1 code Qwen4, reading every unknown from `config.json`, keeping the Qwen3.8
   path bit-identical.
2. **Track B, test weights and package iterations:** prove each step against models whose correct output is known
   (random 27B-wide checkpoints, the frankenmodel), and ship each proven step as a private package iteration.
3. **Track C, orchard:** let the Qwen4 package be the "nearest model", so stage 0 classes the release `weights-only`,
   stage 2 serves it with its own config, and stage 7 packages it.
4. **Track D, release day:** a config-only check, the bring-up, and a fallback for each "not covered" answer.

Tracks A and C are independent until milestone M4; B gives A its tests and C its rehearsal target.

Decisions taken (operator, 2026-11-09): support **4 and 2 chips**; build toward the drop-in **with the full-port fallback
made runnable early**; follow the **existing frankenmodel pattern** (20-layer bf16 checkpoint, generator as written);
release day is a **watcher-started job** run by a scheduled Claude task that notifies the operator; when the Qwen3.8
server holds the chips it **notifies and waits** (it never stops that server); a release the package does not cover
**starts the full-port fallback automatically**.
Standing rules that shape it: only tt-model bundles go on Hugging Face (test weights stay local, in the HF cache layout);
packages follow tt-model-manager's thin-package recipe; orchard changes go test-first with a mutation per guard, as PRs to
`tsingletaryTT/tt-orchard` that the operator merges; hardware only under a gozer lease.

Timing: the day-1 path (Track A through M5) is about **6 weeks** of focused work. If Qwen4 drops sooner, the
release goes through the fallback (M0) and the drop-in path continues.

## Track A: model code (`thin/src` branch `qwen4`, ops repo branch `qwen4`)

Design (validated against the code): **each device holds a column slice of all 4 streams** (width W = 5120/tp per
stream, device-local residual `[S, 4·W]`). The mixed block input comes out K-sharded, which is exactly what today's fused
all-gather+matmul in-projections take, and block outputs stay hidden-sharded, so **no block collective changes**. TP=2 is
the same code with W = 2560. Per hyper-connection site: local per-stream sum of squares → tiny all-gather of the stats →
normalise with γ' = (1+w)/4 → one matmul `xn' @ [W_down | W_inj]` (N padded to 768) → true all-reduce of `[S, 768]`
(use `all_reduce_async`; `tt_all_reduce` on 1xN meshes only reduce-scatters, `v1/ccl.py:174-194`) → u = silu, β =
2·sigmoid → G = sigmoid(u @ W_up) → h = Σᵢ Gᵢ ⊙ xn'ᵢ → block → xᵢ += βᵢ · y. The final mixer is the same without β.

## Track D: release day

- **D1 `tt-orchard drop-check <repo> --bundle <package>`**: accepts only the `Qwen` organisation (lookalike repos with a
  malware zip appeared on 2026-11-09); downloads only `config.json`, `generation_config.json`, tokenizer files and the
  weight index; runs the A2 adapter's validation and the C1 rules; answers **covered**, **covered with notes** (e.g. no
  MTP, context capped at 2048 because QSA is present), or **not covered** with each reason and its fallback command;
  writes JSON. Built in M0 against the Flash-Next config and the fixture.
- **D2 runbook** `docs/runbooks/qwen4-drop-day.md` (tt-orchard): stop the Qwen3.8 server (ports 20000/20001), free host
  memory for the 27B CPU reference (~54 GB bf16; /dev/shm currently holds 116 GB not orchard's), drop-check, bringup,
  review, push, publish on the operator's yes, restart the Qwen3.8 server if wanted.
- **Decision tree**: covered → `bringup --base mando2222/qwen4-27b-dense-v6-thin`; new `model_type` → C7 venv first;
  experts, n-gram/PLE, or anything the adapter refuses → fallback `bringup … --full-port` with the helper (M0); same
  architecture as Qwen3.8 → `bringup --base mando2222/qwen3.8-27b-dflash2-vision-p300x2-q4kv-v6-thin` (works today).
- **D3 the drop watcher** (armed at M0, so an early release gets the fallback automatically; switches to the drop-in
  once M5 passes):
  - **Script** `tt-orchard drop-watch` (in tt-orchard, test-first): one idempotent tick with a state file
    (`~/orchard-runs/qwen4-watch/state.json`) so repeated ticks never start a second run. States: `waiting` → `seen` →
    `checked` → `waiting-for-chips` → `running` → `ready` / `blocked`.
  - **Seeing the release**: the Hub API, `Qwen` organisation only; target `Qwen/Qwen4-27B`, other `Qwen4-27B*` names
    (FP8, Base) are reported and not run. "Complete" means `config.json`, the weight index and every shard it lists are
    present with their sizes, and the last commit is at least 30 minutes old (upload finished); the run pins that commit.
  - **Check**: runs D1; the result decides the route (decision tree above). A new `model_type` with no reference venv
    ready is reported and waits for the operator.
  - **Chips**: if gozer shows the boards held (the Qwen3.8 server, or anyone else), it notifies the operator and waits;
    on a later tick, once all four chips are free, it starts the run and notifies again. It never stops another holder.
  - **Run**: starts `tt-orchard bringup …` in the background (always unattended; a blocked run exits with its code),
    then reads `python3 -m orchard.supervisor status --run-dir … --json` each tick.
  - **Notify**: the scheduled Claude task wraps the script every 30 minutes and sends a push notification on each state
    change (release seen, check result, waiting for chips, run started, stage results, ready or blocked with the reason).
  - **Never**: publishes, pushes a package, uses the operator's HF token for the download, stops another lease holder,
    or downloads from any organisation other than `Qwen`.

## Out of scope

Mixture-of-experts 27B; n-gram/per-layer embedding (Flash-Next's table is 51B parameters); speculative decoding with
Qwen4's MTP head or a retrained drafter; vision; FP8 weights. drop-check reports each of these.

## Risks

- The release may differ from the `qwen4_exp` reading (the community QSA release already applies `k_norm` before pooling,
  which `qwen4_exp` does not); strict tensor accounting and drop-check catch it.
- Decode speed: hyper-connection weights add 1.7 GB read per token per device at TP4 in bf16 (Stage B addresses it).
- The seams could break the exact Qwen3.8 match; one PR per seam, gate on each.
- Host memory on release day (stage 1 CPU reference ~54 GB; ~56 GB free today).
- Release earlier than 6 weeks: fallback route, then the drop-in path continues.

## Appendix A: the Qwen4 reference (transformers 5.19.0 `qwen4_exp`)

Streams stream-major, `X0 = embeds.repeat(1,1,4)`. `hc_norm` per-stream RMSNorm with (1+w), fp32. u = silu(W_down·Xn/4),
G = sigmoid(W_up·u), h = mean over streams of G ⊙ xn; β = 2·sigmoid(W_inj·Xn/4); post xᵢ += βᵢ·y on the un-normed
streams; final `hyper_connection_mixer` = pre-mix only; no input/post-attention/final norms. Shapes: `hc_norm` [4H],
`input_mix_weight_down` [r,4H], `input_mix_weight_up` [4H,r], `block_inject_weight` [4,4H]. QSA: `index_qk_proj`
[(4+1)·128, H], q_layernorm + rope on 64 dims, raw keys cached, blocks of 4 visible tokens pooled by mean → k_layernorm →
rope at block start, score Σ_heads relu(q·k)/√128, top min(512, complete blocks) blocks plus the incomplete tail; exact
full attention up to 2051 tokens. Delta-net as Qwen3.5 except the gate uses `output_gate_type` (Qwen3.8's `swish` is not
accepted by the class). Silent-default traps: missing `num_experts` builds 512 experts, missing `rope_theta` gives 10000,
missing `partial_rotary_factor` gives 1.0, missing `output_gate_type` falls back to `hidden_act`.
